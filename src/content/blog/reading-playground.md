这不是一篇准备发布的正式文章，而是一张可以慢慢往下翻的试读页。你可以把它当成将来写技术笔记时的样子：有连续的中文正文，也有需要停下来看的代码、表格和补充材料。

**先试三件事：** 展开下面的完整日志，在代码窗口里滚动，再把它收起来；切换一次深浅色；把窗口缩窄，看看文字和表格是不是仍然舒服。这篇草稿可以随时删除，不影响其他文章。

## 一、先读一小段正文

做一个 TCP 小实验时，最容易让笔记变长的，往往不是某个复杂结论，而是沿途积累的细节。连接什么时候建立，消息在哪里被读取，为什么一次读取没有拿到完整内容——每一个问题都值得记下来，但它们不一定都应该挤在主线里。

我更喜欢先写清楚“这次想确认什么”，再把完整日志和较长的解释放到读者可以自行展开的位置。第一次阅读时，文章像一条清楚的小路；需要复现时，旁边又留着足够完整的材料。**折叠不是为了藏住信息，而是把阅读顺序交还给读者。**

这里也混入一些日常会出现的名字：TCP、WebSocket、Astro、GitHub，以及行内代码 `const message = '一点薄荷'`。它们和中文放在一起时，不应该显得突然变大、变小，或把一行的高度撑开。

> 一篇技术笔记不必一次解释所有事情。先让人知道问题是什么，再让细节出现在需要它的地方。
>
> ——这是一段用于试读的示例引用，不是外部引文。

### 从一个短片段开始

短代码应该保持自己的高度，不必因为长代码需要滚动，就让每个窗口都占据半个屏幕。

```js title="hello.js"
const message = 'Hello，一点薄荷'
console.log(message)
```

注意代码右上角的复制按钮。你可以复制这两行，看看复制出来的是纯代码，还是混入了文件名和界面文字。

### 不折叠的长代码

不是每个长片段都需要默认收起。下面这份配置直接展示，超过 400px 的部分在框内滚动。可以对比一下，你更喜欢“先看见代码”，还是“先看见一句概括”。

```yaml title="experiment-notes.yml"
# 仅用于试读，不是站点实际配置。
experiment:
  name: tcp-reading-sample
  purpose: observe-message-boundaries
  environment: local-only

client:
  host: 127.0.0.1
  port: 8080
  encoding: utf-8
  connect_timeout_ms: 3000
  read_timeout_ms: 5000

messages:
  - id: greeting
    text: Hello，一点薄荷
    repeat: 1
  - id: small-payload
    text: 一条短消息
    repeat: 3
  - id: multiline-payload
    text: |
      这是第一行。
      这是第二行。
      换行符也只是传输内容的一部分。
    repeat: 1

observations:
  record_connection: true
  record_message_size: true
  record_elapsed_time: true
  include_raw_payload: false

notes:
  - 先记录实际观察，再解释原因。
  - 不把模拟数值写成真实测量结果。
  - 原始日志较长时，可以放进折叠区域。
  - 主文保留读者理解结论所需的信息。

output:
  format: json
  filename: reading-events.json
  pretty_print: true
```

## 三、长文本：把补充材料留在旁边

正文只需要说明主线：TCP 提供的是有序的字节流，应用需要按自己的协议识别消息边界。下面把一段较长的复盘收起来，你可以展开后在文本框里滚动。短一点的补充说明也能用同一种写法，不会被强行撑高。

<details id="sample-text-fold">
<summary>展开实验复盘与写作笔记（长文本，可上下滚动）</summary>
<div class="scroll-content" tabindex="0" role="region" aria-label="实验复盘与写作笔记">

**第一步：先说清楚问题。** 我们想观察的不是“网络快不快”，而是一次发送和一次读取之间到底是什么关系。这个问题越具体，记录时越容易判断哪些信息有用，哪些只是热闹。

**第二步：把环境记下来。** 同一台电脑上的客户端和服务端、两台不同的机器、或者经过代理的连接，都可能呈现不同的时序。记录环境不是为了让文章显得严谨，而是给以后复现的人一个起点。

**第三步：分清事件和解释。** “这次读取返回了 128 字节”是观察；“发送端只发了 128 字节”则可能是未经验证的推断。写笔记时把两者分开，后来回看才不会被自己的措辞带偏。

**第四步：保留消息边界。** 应用层可以约定长度前缀、分隔符或固定长度。选哪一种取决于协议的约束，不能只因为某次读取刚好拿到完整消息，就假定以后都会如此。

**第五步：不要用一次成功代替验证。** 本地实验很容易连续成功，但网络、调度和缓冲条件发生变化后，原来的假设未必成立。一个好的例子应该让假设可见，而不是让偶然看起来像规则。

**第六步：日志先求可读。** 时间、方向、长度和必要的上下文通常已经足够。完整负载可能很大，也可能包含不该公开的信息；复制日志到文章之前，要先确认它只是测试材料。

**第七步：模拟数据要说明。** 这篇文章里的事件和数值都是为了排版而准备的示例。它们不构成吞吐量、延迟或稳定性的证据，也不应该被拿去比较不同实现。

**第八步：把主线留下。** 如果读者只看正文，也应该知道问题、方法和结论。折叠区域适合放完整日志、补充推导和较长的复现材料，不适合藏住安全提醒或关键前提。

**第九步：别让代码淹没文章。** 代码窗口能够滚动以后，页面会更短一些，但窗口本身也不宜过高。你现在可以试试：先读这段文字，再回到上面的长代码，比较两种区域的阅读手感。

**第十步：手机上重新看一次。** 桌面屏幕上顺眼的表格，到了手机上可能需要横向滑动；长文件名和一整行命令也更容易暴露问题。预览不只是确认“内容出现了”，还要确认读者能顺利读完。

**第十一步：用键盘试试。** Tab 可以移动到折叠标题，Enter 或空格负责展开、收起。进入这个滚动区域后，可以用方向键或 PageDown 翻看，不需要一直依赖鼠标滚轮。

**第十二步：给未来的自己留一点线索。** 写完以后，把最容易忘的前提、没验证的边界和下一次要做的实验记下来。它们不需要很长，但通常比漂亮的总结更有用。

最后可以回到主文。点击外面的“展开实验复盘与写作笔记”即可收起这一块，不需要把内部滚动条拖回顶部。

## 六、公式、列表与阅读节奏

公式不一定经常用，但最好提前确认。行内公式可以像这样放进句子里：平均耗时记为 $\bar{t}$；它的字号和行高应该与正文协调。

块级公式单独占一段：

$$
\bar{t} = \frac{1}{n} \sum_{i=1}^{n} t_i
$$

这里的公式只展示平均值的写法，并不意味着上面的模拟数据已经完成统计验证。

### 可以顺手试一遍的操作

1. 从目录跳到“长代码”，再跳到“宽表格”。
2. 展开 JSON，滚到末尾，点复制按钮检查是否包含第 9 条记录。
3. 展开长文本，滚动几段后直接收起。
4. 将浏览器窗口缩窄，或用手机打开本地预览。
5. 切换深浅色，看看正文、代码和图片的对比。
6. 只用 Tab、Enter、空格和方向键完成一次展开与滚动。

- **主线内容**：适合直接放在正文。
  - 问题是什么。
  - 用什么方法观察。
  - 结论有哪些前提。
- **补充材料**：适合按需折叠。
  - 完整代码和日志。
  - 复现步骤的详细输出。
  - 不影响主线的推导和背景。

## 七、读到最后，再看看哪里不舒服

如果你能自然地读到这里，没有被突然变宽的内容打断，也没有为了略过一段代码连续滑动很久，那这篇样稿就完成了它的任务。你不必逐个检查所有细节，先记住最直观的感觉：字是不是太密，段落是不是太松，折叠标题是不是一眼能看懂。

可以直接告诉我“代码框再矮一点”“正文行距有点大”或“手机上表格不好滑”。这些具体感受，比一次添加更多功能更有价值。

# 用 Typora 写博客

## 平时只做这些

1. 启动一次本地预览：`pnpm dev`。服务运行时不用每篇重新启动。
2. 用 Typora 在 `src/content/blog/` 保存 `.md` 文件；短记保存到 `src/content/shorts/`。
3. 文件名就是默认标题。直接写正文，保存后刷新博客预览即可。

例如 `src/content/blog/一次有趣的调试.md`：

```md
今天解决了一个小问题，记录一下过程。

## 遇到了什么

这里写正文。

## 怎么解决

这里继续写。
```

不需要 YAML 头、标题配置、日期、阅读时长或目录配置。文章页面已有标题，正文不必再重复一个同名一级标题。默认标题仍受原规则约束：非空、最多 60 个字符。

## 博客自动负责什么

- 标题：文件名去掉 `.md`／`.mdx`；手填 `title` 时以手填为准。
- 发布日期：Git 中该文件沿历史追溯的首次提交时间，按现有 UTC 规则显示。
- 更新日期：Git 中该文件最近一次提交时间。自动值只有晚于发布日期且跨 UTC 日期时才显示，避免首次发布就重复标注 Updated。
- 新文件尚未提交时：本地暂用文件修改时间预览；首次提交后以 Git 为准，不会把本地预览日期误当成永久发布时间。
- 阅读时长、目录、搜索：沿用站点现有默认处理。正文有小标题时生成目录，公开且允许搜索的正文由生产构建生成索引。

自动信息只在读取时补全，**不改写 Typora 正在编辑的文件，也不修改正文**。已有的标题、日期、`lastModDate: ''` 等显式配置都保留；填错的值仍会报错，不会被自动修正掩盖。

## 草稿和发布

- 不准备参与博客的文件，可以用 `_` 开头命名，例如 `_还没写完.md`，它不会进入内容集合或预览。
- 想在博客中预览草稿但不公开，文件开头只加：

  ```yaml
  ---
  draft: true
  ---
  ```

- 默认普通文章可进入生产构建；**保存本地文件不会自动上线**。确认内容完成后，仍按现有 Git 提交、检查和发布流程操作。推送 `main` 可能触发部署，不能当作无副作用的备份。
- Git 提交后如果只变了历史、没有改正文，正在运行的开发服务不一定立即重读日期；重新启动预览或运行构建会更新。正式构建始终重算，不复用旧日期缓存。

## 偶尔需要手动指定

仍然可以加可选 frontmatter，例如导入一篇旧文章：

```yaml
---
title: 自定义标题
pubDate: 2020-05-01
lastModDate: ''
---
```

没有写的字段才自动补。`lastModDate: ''` 表示不显示更新时间。

文件名会影响默认 URL；文章发布后不要随意改文件名。Git 通常能追溯普通重命名的首次提交，但它不自动维护旧网址重定向，也不保证在大幅改写后识别重命名。

## 构建与部署

- 正常 `pnpm build` 自动准备 `.post-dates.json`，不需要编辑或提交它。
- GitHub Actions 使用完整历史，自动准备 Docker 所需的日期快照。
- 手动 Docker 构建前，在完整 Git 工作区运行 `pnpm content:dates`。快照与原文哈希必须匹配；没有 Git 又缺失或过期的快照时构建明确失败，不使用构建机器的文件时间编造日期。
- Git 历史被裁浅时需要补全（`git fetch --unshallow`）。Git 日期是提交时间，不是文件实际开始写作或第一次对外发布的证据；需要真实发布日期时可手动覆盖。
